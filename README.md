# RAG Evaluation Harness

A reusable harness that scores the answers of a RAG system for **faithfulness** (is every claim supported by the retrieved context?) and **relevance** (does the answer address the question?) on a fixed 100-query test set. It stores every run in SQLite, compares runs with confidence intervals and exact paired tests, flags a subset of answers for human review, and shows trends in a Streamlit dashboard.

It ships with a small config-driven RAG pipeline (an HR-policy question answerer over a fictional company) as the system under test. The harness only calls one function, `answer(question, config)`, so it can evaluate any other RAG system that honours the same contract.

**Status.** Complete through the dashboard. Every judge-based number in this repository comes from LLM judges that are **not calibrated against human labels** (the calibration attempt was inconclusive; see [Judge calibration](#9-judge-calibration)). Read every rate as "what the judge measured", not as a verified rate.

## 2. What these results support, and what they do not

**Supported by the stored runs**
- The harness works end to end: a run produces answers, deterministic checks, claim-level faithfulness judgements and rubric relevance judgements, all stored and queryable with SQL.
- The measured starting point (`configs/v0.yaml`, dev split) is the baseline row in the table above, with its interval.
- Retrieval is near its ceiling on this small corpus, so the experiments could not move retrieval much; the ungrounded answers of the baseline are generation errors by the judge's account (the source chunk was in the prompt).
- Changing only the prompt to number the chunks and ask for `[n]` citations gave the lowest ungrounded rate among the dev experiments that did not make other metrics worse. It is a point estimate with an interval that overlaps the baseline's.

**Not supported**
- *"The change is a proven improvement."* On dev the exact paired p of the chosen change is above 0.05, the noise control (same config, only the sampling seed changed) already moved the count on its own, and the chosen config was the best of 12 dev looks with no multiple-comparison correction, so its dev rate is optimistic. On the 20 held-out queries the verdict is `not_distinguishable`: one answer separates the two runs.
- *"The rates are the true share of hallucinated answers."* The judges are uncalibrated. The calibration comparison had zero positive cases on both sides, so it says nothing about whether the judges detect an ungrounded answer.
- *The CV draft.* The author's CV draft figures (an ungrounded rate falling from 25% to 12%, and 10-15% of answers flagged for review) were hypotheses, not targets, and no stored run supports them. The measured baseline is already far below 25% (see the table), and the flag rate in the stored regression checks is a review-workload figure that depends on which two runs are compared. The CV follows the measurements in this README, not the other way round.

## 3. Architecture

Two halves joined by one contract:

```
SYSTEM UNDER TEST (rag/)
  docs -> chunker -> embedder -> FAISS (+ BM25, reranker, query rewrite: off in v0) -> retriever
       -> prompt builder -> LLM -> answer

THE CONTRACT
  answer(question: str, config: dict) -> {
      "answer": str,
      "chunks": [{"chunk_id", "doc_id", "text", "score"}],
      "latency_ms": float
  }

EVALUATION HARNESS (evalharness/)
  test set -> runner -> deterministic checks + LLM judges -> SQLite
           -> regression compare + flagging -> Streamlit dashboard

SHARED LLM CLIENT (llm/)
  llm/client.py: generate() with cache, retries, token + latency log.
```

- `rag/` knows nothing about evaluation and never imports `evalharness/`. The harness reaches the system only through the names in `configs/harness.yaml` (`system.answer`, `system.load_config`, `system.describe`), loaded with `importlib`.
- `llm/client.py` is the single door to any model. Every call is cached in SQLite, keyed by a hash of the endpoint, model, model digest, prompt, temperature, JSON schema, seed and reasoning effort, so re-runs are cheap and repeatable. Failed, cut-off or schema-invalid replies are never cached.
- Every run stores its run id, timestamp, git commit hash, dirty flag, full config, test-set hash and scorer versions in `runs`.

## 5. Setup and reproduce

Commands marked *(needs Ollama)* call a local or cloud model. The author ran the offline commands in a fresh clone (see below); installing Ollama and signing in were done on the author's machine and were not repeated on a clean one.

**Prerequisites**
- Python 3.13 and `git`.
- [Ollama](https://ollama.com) running locally (`http://localhost:11434`). The embedding model runs locally; the generator and judge are Ollama cloud models, which need an Ollama sign-in (`ollama signin`) and a plan that includes them (the Free plan was used):
  ```bash
  ollama pull nomic-embed-text      # local embeddings, 768-dim
  ollama pull gemma4:31b-cloud      # generator
  ollama pull gpt-oss:120b-cloud    # judge (must differ from the generator)
  ```

**Install and run the offline tests** (no model, no database needed)
```bash
git clone <this repository> && cd <repository folder>
python3.13 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env              # keep the dummy key; Ollama ignores it
python -m pytest -q
python -m evalharness.testset summary     # the 100 queries: counts by type and split
python -m rag.loader                      # the 22 documents load with stable ids
```

**Ask the pipeline one question** *(needs Ollama)*
```bash
python -m rag.pipeline --config configs/v0.yaml --question "How many casual leaves do interns get?"
```
It prints the answer, the retrieved chunks with scores and the latency.

**Pin your model digests (needed once on a new machine).** The configs pin the digest of each Ollama model build, and a run refuses to start if the server reports another one. Read yours with `curl -s http://localhost:11434/api/tags`, copy the full `digest` of each model, and update `generation.model_digest` in the pipeline configs and `model_digest` in `configs/judges.yaml` (faithfulness and relevance blocks). For `-cloud` models the digest identifies the local manifest, not the remote weights. Editing a config changes the SHA-256 pinned in `configs/heldout.yaml`, which is the point: see "Held-out" below.

**Evaluate** *(needs Ollama; the first dev run makes about 80 generator calls and about 220 judge calls)*
```bash
# 1. first run on an empty database: there is no accepted run to compare with yet
python -m evalharness run --config configs/v0.yaml --split dev --no-gate
# 2. record that run as the reference (a human decision, never automatic)
python -m evalharness.regression accept --run-id <RUN_ID> --note "why this run is the reference"
# 3. every later run: generate, check, judge, regression gate; exit 0 PASS, 1 FAIL, 2 cannot decide
python -m evalharness run --config configs/<experiment>.yaml --split dev
# resume the judging and the gate for a stored run after a transient failure
python -m evalharness score --run-id <RUN_ID>
```
The run needs a clean git tree (`--allow-dirty` stores `git_dirty = 1`) and refuses `--split heldout`. The single stages (`evalharness.runner`, `checks`, `judges faithfulness|relevance`, `report`, `experiments compare`, `regression check`) can also be run on their own; each prints `--help`.

**Dashboard**
```bash
streamlit run dashboard/app.py     # localhost only; needs data/results.sqlite
```

**Held-out split.** The 20 held-out queries were used once per config, in Step 12, under a pre-registration (`configs/heldout.yaml`: the two configs, their file SHA-256, the scorer versions, a limit of one held-out run per config). `python -m evalharness.runner --split heldout --allow-heldout` refuses unless every pin matches. Do not use the held-out split for tuning.

**What will differ on your machine.** You get your own `data/results.sqlite` and cache. Because the generator and judge are cloud models that are not fully deterministic (the same prompt at temperature 0 gave different replies across cache rebuilds), a fresh run will not reproduce the stored numbers exactly; it should land near them, and the intervals above show how near is reasonable. Rebuilding the FAISS index and re-embedding the corpus happens automatically on the first run. The README block in section 1 is generated on the author's machine from the author's database; `python -m evalharness.writeup check` therefore refuses in a clone (no database).

## 6. Metric definitions

Worked examples use made-up numbers to show the arithmetic; they are not results.

- **Faithfulness (groundedness).** Two judge calls per answer. Call 1 splits the answer into atomic claims (it never sees the context). Call 2 labels each claim against the exact retrieved chunks as `supported`, `unsupported` or `contradicted`, giving its reasoning first. `faithfulness = supported claims / total claims` (1.0 when the answer has no factual claim, for example a refusal). Example: 3 of 4 claims supported gives 0.75.
- **Ungrounded.** An answer is ungrounded when `faithfulness < 0.8` (the configured threshold, `configs/judges.yaml`) **or** any claim is `contradicted`. The headline metric is the ungrounded rate = ungrounded answers / judged answers.
- **Relevance.** One judge call scores the answer 0, 1 or 2 against a rubric (it sees the question and answer only). `relevance = score / 2`; an answer is `irrelevant` when the score is 0. A correct refusal of a question the policies do not cover scores as relevant; a refusal of a question they do cover scores 0 (a *false refusal*). An invented answer to an unanswerable question is irrelevant and ungrounded.
- **Retrieval metrics** (no LLM; the test set stores the correct source documents). `hit@k` is 1 if a source document appears among the first k chunks. `MRR` is the mean of `1 / rank` of the first source chunk (0 if none). `in_context` is 1 if any source chunk reached the prompt. Example: chunk documents `[a, a, b, c]`, source `[b]`: first source rank 3, hit@1 = 0, hit@4 = 1, reciprocal rank 1/3.
- **Failure cause of an ungrounded answer.** Answerable and no source chunk in the prompt: `retrieval_miss`. Answerable with a source chunk in the prompt, or unanswerable: `generation_error`.
- **Refusal check.** A list of refusal phrases matched against the answer. It is a heuristic, not a judgement.
- **95% Wilson interval** for a rate `k / n`, with `p = k / n` and `z = 1.96`:
  `center = (p + z^2/(2n)) / (1 + z^2/n)`, `half = z * sqrt(p(1-p)/n + z^2/(4n^2)) / (1 + z^2/n)`. Unlike `p ± z*sqrt(p(1-p)/n)` it stays sensible at `p = 0` or `p = 1` and for small `n`.
- **Exact paired test.** Two runs answer the same queries, so each query is unchanged or its ungrounded flag *flipped*. With `n` flips and `k` in the majority direction, `p = 2 * P(X >= k)` for `X ~ Binomial(n, 0.5)` (capped at 1). Example: 4 improved and 1 regressed gives n = 5, k = 4, p = 0.375: not distinguishable from no change. The mean faithfulness difference comes with a seeded paired bootstrap interval.
- **Flag reasons** (Step 13): `ungrounded`, `low_relevance` (relevance below 0.75), `judges_disagree` (the refusal check and the relevance judge contradict each other), `answer_changed` (word-level similarity to the accepted run's answer below 0.6, citation markers ignored), `not_judged`. The **flag rate** is flagged answers / answers: review workload, not quality.
- **Gate.** `delta = (ungrounded rate of the new run − of the accepted run) * 100` in percentage points; FAIL when `delta` is above 3.0 (configurable). One answer is `100 / n` points, so a 3-point gate trips on a handful of answers and can trip on sampling noise.

## 7. Method

- **Corpus.** 22 synthetic HR policy documents for a fictional company (about 7,000 words), with checkable facts (numbers, dates, eligibility rules) and deliberately confusable pairs (employee leave vs intern leave, expense reimbursement vs travel, and so on). A few topics are never mentioned, so unanswerable queries are truly unanswerable.
- **Test set.** 100 queries: lookup, multi-chunk, paraphrased/vague and unanswerable, each with a reference answer and source document ids (empty for unanswerable), validated with pydantic. Split once, stratified by type, into 80 dev and 20 held-out. All 100 were reviewed by the author.
- **System under test (v0).** Word-window chunks (150 words, 30 overlap), `nomic-embed-text` embeddings, a FAISS inner-product index over normalised vectors, top 4 chunks, a plain prompt, generator `gemma4:31b-cloud` at temperature 0.0 and seed 42. v0 is a plain baseline, not pre-optimised.
- **Judges.** `gpt-oss:120b-cloud` (a different, larger model than the generator) at temperature 0, seed 42, reasoning effort medium, prompts versioned in `configs/judges.yaml`. Every score row stores the judge version, so results from different prompts are never mixed.
- **Statistics.** Rates carry 95% Wilson intervals; paired run comparisons use the exact sign test on flipped queries; nothing is rounded differently from the stored report.

## 8. Experiments

Each experiment is one YAML file in `configs/` that differs from `configs/v0.yaml` in **exactly one declared variable** (`python -m evalharness.experiments check --config ...` enforces this), with the hypothesis written before the run. All runs use the same test set, the same cached judge settings and the same scorer versions.

How to read the table in section 1:
- The `seed 42 -> 43` row is a **noise control**: the same configuration with only the sampling seed changed. Its change shows how far the numbers move with no real change.
- Several runs lower the ungrounded rate partly by refusing more (see *False refusals*), so a lower ungrounded rate alone is not a win.
- The selection rule for the config taken to the held-out set was fixed before the results: the lowest ungrounded rate among runs whose bad-answer rate and false-refusal count are not worse than the baseline, noise control excluded.
- Twelve runs were compared on the same 80 queries, with no multiple-comparison correction, so the best one looks better than it is. Only one row has an exact p below 0.05, and it also has more false refusals than the baseline.
- Retrieval experiments (chunk size, overlap, top-k, hybrid BM25 + vector, cross-encoder reranker) could not improve retrieval much because retrieval was already near its ceiling here; `chunk_size 300` and `chunk_overlap 0` made retrieval worse.
- Citation correctness (whether `[n]` points to the chunk that supports the sentence) is not scored.

## 9. Judge calibration

An LLM judge is only trustworthy after it is compared with human labels. The procedure (`python -m evalharness.calibration`): the 80 dev answers were split once into `tune` and `check` (seeded, stratified); the author labels answers **blind** (the tool shows the question, the answer and the retrieved chunks, never the judge's output); prompt changes may be justified only by `tune` disagreements; the chosen version is reported once on `check`. Agreement, precision and recall on "ungrounded", and Cohen's kappa are computed (kappa is hand-written, with a seeded bootstrap interval).

**Result: inconclusive.** The first labelling pass was too fast to be careful and was discarded. The second labelled 20 `check` answers, all as grounded and relevant. The judges also flagged none of those 20, because every judge-flagged answer had been shown in a chat session and was therefore forced into `tune`. The comparison has **zero positives on both sides**, so precision, recall and kappa are undefined (shown as `undefined (0/0)`, never 0 or 1); the agreement is only that both sides call the same 20 answers grounded. See the calibration table in section 1 and `experiments/calibration.md`. Consequently both judges stay **uncalibrated**, every judge-based number in this repository is labelled that way, and a real calibration (careful labels that include judge-positive answers) is left open. Human labels must come from the author; no LLM labelled anything.

## 10. Regression check, flagging and gate

`python -m evalharness.regression check --run-id <ID>` compares a new dev run with the **accepted** run (a stored human decision, not "the previous run"), flags answers for review (reasons in section 6), writes the flags to the `reviews` table and prints a PASS/FAIL gate. It refuses incomplete data instead of passing, never accepts a run by itself and refuses held-out runs. `python -m evalharness.regression thresholds` reports flag precision and recall against the author's labels: with no human "ungrounded" label they are undefined, so the thresholds are **starting defaults, not tuned values**. The stored checks are in the section 1 table.

## 11. Dashboard

`streamlit run dashboard/app.py` shows four pages over the stored database: **Trends** (dev runs as points with Wilson error bars, held-out in a separate read-only table), **Run vs run** (paired counts, exact p, both answers side by side), **Review queue** (flagged answers one at a time, OK / Bad buttons and notes saved to `reviews`; the judge's reasoning is collapsed so you form your own view first) and **Breakdown by type** (intervals, n, failure causes). It computes no metric itself, makes no LLM call and writes only the human fields of `reviews`. Review labels are triage labels on flagged answers: they say how often a flag was right, not how many bad answers the flags missed, and they are not calibration labels.

## 12. Limitations

- Both judges are **uncalibrated** (section 9); the rates are the judges' measurement, not verified rates.
- Synthetic corpus of one fictional company, 22 documents; results may not carry over to real documents.
- 80 dev and 20 held-out queries; per-type sample sizes are 12-16 on dev and 3-10 held-out, so per-type differences are inside the intervals. On 20 queries one answer is 5 percentage points.
- The chosen config was the best of 12 dev looks (winner's curse); the held-out confirmation could not distinguish it from the baseline.
- Each answer is one sample from a cloud model that is not fully deterministic; the model digest is a local manifest, not a hash of remote weights. Re-runs here are identical only because the cache serves them.
- Refusal detection is a phrase match; citation correctness is not scored; latency comes from the generator call and the retrieval step only.
- Flag precision and recall against human labels cannot be measured yet (no human "ungrounded" label exists), so the flag thresholds are untuned.
- The CI workflow runs only the offline tests: CI has no Ollama server and no results database, so it cannot run an evaluation or the regression gate.
- A single author labelled and reviewed everything.

## 13. Design decisions

- **Own judges, not RAGAS or DeepEval.** Every prompt, claim verdict and reasoning is visible, versioned and stored, so a score can be traced to claims. The judges are still uncalibrated; that is a measurement gap, not a hidden one.
- **No LangChain for the pipeline.** Its wrappers hide the retrieved chunks and scores the harness must see.
- **Cache every LLM call.** Cloud models drift; the cache key makes re-runs repeatable and cheap, and failed or invalid replies are never cached.
- **Judge model different from (and larger than) the generator.** Avoids a model grading its own writing.
- **Held-out used once.** Pre-registered configs and SHA-256 pins, a limit of one held-out run per config, and fail-closed guards in the runner, so the 20 queries stay unseen until the confirmation.
- **One variable per experiment, plus a noise control.** Otherwise a change cannot be credited to its cause, and noise cannot be told from effect.
- **Wilson intervals and an exact paired test** instead of the normal approximation and an unpaired comparison: both are wrong at these sample sizes.
- **Thresholds are not tuned on labels that do not exist.** Starting values are shipped as such and say so.
- **Cross-encoder reranker in a child process.** On macOS, `faiss-cpu` and `torch` each bundle `libomp` and cannot share a process; the reranker runs in its own process instead of setting `KMP_DUPLICATE_LIB_OK`, which can give incorrect results.

## 14. Troubleshooting

- **`402 Payment Required`** from a model: that cloud model is not in your Ollama plan. This project uses `gemma4:31b-cloud` and `gpt-oss:120b-cloud`.
- **A run refuses with a digest mismatch:** pin your own digests (section 5).
- **The run refuses on a dirty tree:** commit, or pass `--allow-dirty` (stored as `git_dirty = 1`).
- **`OMP: Error #15` or a silent crash:** `faiss` and `torch` were imported into one process. Keep them separate; do not set `KMP_DUPLICATE_LIB_OK`.
- **`ContextLimitError`:** the prompt reached `generation.max_prompt_tokens` (3500) or the server reported no token count. It is counted as a failed output, never dropped.
- **Connection errors:** Ollama is not running at `http://localhost:11434` (`configs/llm.yaml`).
- **A judge reply failed validation:** such replies are not cached; rerun `python -m evalharness score --run-id <ID>` to retry only the failed items.
- **`python -m evalharness.writeup check` says there is no database:** expected in a fresh clone.
